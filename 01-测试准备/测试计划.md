## 一、项目背景与测试目标

德尚 DS·O2O 外卖版为 ThinkPHP 传统 MPA + AJAX 混合架构的本地生活平台，覆盖买家端、商家端、平台后台三端。本次测试针对其**核心交易链路**开展系统测试，目标是：

1. 验证买家「注册/登录 → 定位 → 找店 → 选品 → 加购 → 下单」主链路可用；
2. 验证商家「入驻 → 审核开店 → 发布商品 → 配送设置 → 接单」链路可用；
3. 验证跑腿（帮买/帮送）发单链路可用；
4. 识别接口层的参数校验缺失、越权、幂等失效与注入类安全问题；
5. 输出可复用的用例资产与可跟踪的缺陷清单，为发布决策提供依据。

**测试定位**：接口测试为主（占主要工作量），页面功能验证为辅，用于确认接口行为与页面的实际一致性。

| 03 | 外卖浏览与交易 | 定位、附近商家、店铺详情、商品详情、购物车、结算、下单、配送距离校验 |
| 04 | 商家端与订单流转 | 商家登录、个人商家入驻（4 步向导）、后台审核、商品发布、配送设置、配送员管理、订单查询与处理 |

### 2.2 范围外（本轮不测，避免范围蔓延）

- **真实支付与资金流转**：不触发真实扣款，仅验证下单前的订单生成与金额计算；
- **第三方通道**：短信通道、物流轨迹、地图服务的服务商侧行为（仅测我方调用与返回处理）；
- **性能与压力**：不测并发、响应时间、稳定性基线；
- **兼容性**：不做多浏览器/多机型矩阵；
- **平台后台非交易类功能**：仅覆盖与开店审核、订单流转相关的页面。

## 三、测试策略

### 3.1 测试依据与断言口径

以 `02-需求与接口分析/` 的抓包工作稿为**唯一事实依据**（无正式 PRD），断言按响应形态分三类：

| 响应形态 | 适用场景 | 断言方式 |
|---|---|---|
| AJAX JSON | 登录、下单、增删改等异步操作 | `code=10000` 成功，`code=10001` 业务失败，结合 `message` 判定 |
| 表单跳转页 `dispatch_jump` | 传统 form POST（入驻、地址等） | `.system-message .success/.error` 判定，`.detail` 看详情，`.jump` 看跳转 |
| 纯文本 | 校验类接口（`check_member` 等） | 返回 `true` / `false` 或中文错误文案 |

鉴权形态为 Cookie-Session（PHPSESSID），无独立 token，故所有用例需显式覆盖**未登录、登录态过期、退出后旧 Cookie 复用**三类前置。

### 3.2 测试类型矩阵

| 类型 | 设计要点 |
|---|---|
| 正向 | 必填齐全 + 合法值，验证主流程可达 |
| 异常 | 空值、缺失、非法格式、类型错误、多余参数 |
| 边界 | 长度上下界与越界值（±1/±2）、数值上下界、日期先后关系 |
| 业务规则 | 配送距离超限、地址数量上限、重复提交幂等、订单状态流转合法性 |
| 安全 | SQL 注入、XSS、越权访问他人资源、遍历/枚举 |
| 权限 | 未登录访问、跨角色访问（买家调商家接口） |

### 3.3 优先级与抽样策略

按业务影响分三级，P0 全量执行，P1 抽样，P2 取典型：

| 级别 | 定义 | 抽样策略 |
|---|---|---|
| P0 | 阻断级，核心主干流程，缺陷即整链不可用 | **100% 保留执行** |
| P1 | 次要核心功能与高频异常 | 抽样执行（按等价类代表值） |
| P2 | 次要边界、极端异常、低概率场景 | 仅取代表性典型 |

**补充策略**：对 01 鉴权链路在首轮抽样后**追加全量执行**（新增 89 条），因该模块为所有链路的入口，入口失效则后续断言全部无效。

### 3.4 执行顺序

先冒烟后铺开：**鉴权 → 基础数据 → 浏览与交易 → 商家端 → 跑腿**。任一环节出现主干阻断（如 SQL 1364 类错误），立即记录缺陷并评估其后链路是否降级为阻塞，避免继续产出无效执行记录。

| 指标 | 标准 |

## 八、风险与应对

| 风险 | 影响 | 应对措施 | 实际发生 |
|---|---|---|---|
| 环境功能未开启（手机注册/登录/找回密码） | 相关用例无法取得有效断言 | 判定为**阻塞而非缺陷**，单独统计并在报告中列明补测条件 | 是，35 条阻塞 |
| 主干链路致命缺陷（SQL 1364） | 下单/接单/跑腿发单整体阻断，后续用例无法验证成功态 | 立即提缺陷并升级为冒烟阻断项；后续用例按错误态设计断言 | 是，3 条链路阻断 |
| 无正式 PRD，仅抓包文档 | 需求与实现不一致时缺判定依据 | 以实测行为为准并记录差异（如用户名长度 3-15 位 vs 实际 3-13 位），推动文档修订 | 是，1 处规则不一致 |
| 单执行人、无自动化 | 执行周期长、回归成本高 | 用例结构化（编号+请求数据+预期结果），便于脚本化复用；按 P0 优先保证主干覆盖 | 待确认（人力信息未留档） |
| Cookie-Session 鉴权 | 用例间会话相互污染 | 用例前置显式声明登录态；退出/过期场景单独建用例 | 是，已覆盖 |
| 环境数据被多轮测试污染 | 地址上限、购物车等用例结果不可复现 | 记录数据基线，执行后清理新增数据 | 待确认 |
